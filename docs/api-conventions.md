# API Conventions

**Status:** Accepted MVP baseline
**Decision record:** `docs/decisions/0002-api-conventions.md`

## Versioning and Routes

- Product APIs use the `/api/v1` prefix.
- OpenAPI JSON is available at `/api/v1/openapi.json`.
- Operational probes remain unversioned at `/health` and `/health/live` so Docker and hosting platforms can call stable infrastructure URLs.
- Resource paths use plural nouns, for example `/api/v1/properties` and `/api/v1/tickets`.
- Nested routes are used only when the child cannot be addressed meaningfully without its parent.

## Success Responses

- A single resource is returned directly as its documented response model.
- Collections use the shared page structure instead of module-specific envelopes.
- Create operations return `201 Created`.
- Successful updates return the updated resource unless the operation intentionally has no response body.
- Delete/archive operations return `204 No Content` only when no response body is needed.

## Pagination

The MVP uses page-based pagination because it is easy for the frontend and sufficient for the expected portfolio sizes.

Request query parameters:

- `page`: positive integer, default `1`;
- `page_size`: integer from `1` to `100`, default `20`.

Response shape:

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0,
  "pages": 0
}
```

Cursor pagination may be introduced later for high-volume message timelines without changing unrelated endpoints.

## Error Responses

Errors use `application/problem+json` and a stable RFC 9457-style structure:

```json
{
  "type": "about:blank",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more request values are invalid.",
  "instance": "/api/v1/properties",
  "code": "request_validation_failed",
  "request_id": "server-generated-uuid",
  "errors": [
    {
      "field": "body.name",
      "message": "Field required",
      "code": "missing"
    }
  ]
}
```

- `code` is stable and intended for frontend behavior or translation lookup.
- `detail` is safe human-readable context and must not expose secrets or internal traces.
- `request_id` is generated by the backend and returned in the `X-Request-ID` header.
- `errors` is optional and used for field-level validation details.
- Authentication and authorization failures use the same structure.

## Authentication and Request Protection

- Authentication uses opaque server-backed sessions sent in an `HttpOnly`,
  `SameSite=Lax` cookie. Only a token hash is stored in PostgreSQL.
- Browser credentials or session tokens must never be stored in `localStorage`.
- The backend derives the active user, role, and `company_id` from the session;
  request data never supplies authorization context.
- Authenticated state-changing requests require the CSRF cookie value in the
  `X-CSRF-Token` header. Login, registration, and invitation acceptance are
  unauthenticated entry points and do not use this session CSRF check.
- Production uses HTTPS and secure cookies. Trusted frontend origins are
  configured explicitly and CORS credentials are enabled only for them.
- Invalid login responses remain generic. Explicit inactive-account errors are
  returned only after the submitted password has been verified.

## OpenAPI Rules

- Every endpoint declares a response model and meaningful status code.
- Routes are tagged by module: Foundation, Properties, Calendar, Messages, Maintenance, or System.
- Request and response models use domain names rather than database-table names.
- Examples must use synthetic data.
- Mock or simulator behavior must be identified in endpoint descriptions.

## Integration Modes

Every external adapter declares one operational mode:

- `simulator`: deterministic local behavior with no external request;
- `test`: provider sandbox, fake server, or controlled fixture behavior;
- `production`: configured real-provider behavior.

The UI and API must never label simulator or test behavior as a connected production integration.

## Compatibility

- Additive optional fields may be introduced within `/api/v1`.
- Removing or renaming fields, changing meanings, or making optional fields required needs a new version or an explicitly coordinated migration.
- Database models are not API contracts; response schemas control what is exposed.
